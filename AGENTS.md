# AGENTS.md: taskq

## О проекте

`taskq` — Go-библиотека для фоновых задач.

- Минимальная версия Go: 1.26
- Модуль: `github.com/denisdubovitskiy/taskq`
- Архитектура: ядро + plugin-интерфейсы (`Broker`, `Backend`, `Locker`, `Logger`, `Tracer`, `Meter`)
- API: generic `Task[T, R]`, `Future[R]`, `Client`, `Worker`, `Registry`, `Scheduler` (`AddEvery`/`AddCron`)
- Оркестрация: `SubmitGroup` (группы), `NewChain`/`Add` (цепочки), `SubmitChord` (аккорды, требует `ChordBackend` в backend)

## Структура

```
taskq/
  ├── *.go                  # ядро: интерфейсы, Task, Future, Client, Worker, Scheduler, оркестрация (group/chain/chord)
  ├── internal/             # внутренние helpers (idgen, backoff)
  ├── internal/cron/        # парсер 5-полевых cron-выражений (используется Scheduler'ом)
  ├── brokers/memory/       # in-memory брокер для тестов
  ├── backends/memory/      # in-memory backend для тестов
  ├── backends/file/        # файловый backend (reference implementation)
  ├── lockers/memory/       # in-memory Locker для тестов
  ├── adapters/slogadapter/ # slog-адаптер: Logger/Tracer/Meter (референс); zap — позже
  └── example/              # примеры: main.go (ядро) + подпакеты <сценарий>/ (scheduler и т.п.)
```

## Приложение-пример

- `example/` должно демонстрировать **абсолютно весь** функционал библиотеки:
  `example/main.go` — ядро (submit, оркестрация, жизненный цикл, очереди),
  подпакеты `example/<сценарий>/` — сложные сценарии (например `example/scheduler`:
  персистентность, catch-up, двойные экземпляры).
- **Обязательное требование**: на каждую добавляемую фичу и любой новый
  функционал (публичный API, опция, интерфейс, состояние, политика) агент
  обязан обновить `example/` — использовать фичу в `main.go` или в отдельном
  подпакете, если сценарий не вписывается в основной поток.
- Новые сценарии, которые требуют «второго процесса», рестарта, нескольких
  экземпляров или заметно удлиняют основной прогон, выносить в подпакет
  `example/<сценарий>/main.go`.
- Все примеры должны компилироваться и запускаться до конца:
  `go run ./example` и `go run ./example/<подпакет>`.
- Перед завершением задачи агент прогоняет **все** примеры и `go test ./...`.

## Принципы

- Ядро зависит только от stdlib.
- Внешние системы подключаются через интерфейсы.
- Использовать generics, минимум reflection.
- `context.Context` — первый аргумент.
- Оборачивать ошибки через `fmt.Errorf("...: %w", err)`.
- Комментарии на русском для экспортированных сущностей.
- Конструкторы возвращают `*Type, error` и валидируют обязательные аргументы.
- Для опциональных параметров — functional options.

## Scheduler — ключевые инварианты

- Планировщик отправляет задачи через `Client.Submit`: ретраи, ETA и backend
  работают, как у обычного Submit.
- Lock от двойного запуска: ключ = имя task + окно тика (для `AddEvery` —
  `fireTime.Truncate(interval)`, для cron — секунда срабатывания). Lock НЕ
  снимается досрочно — удерживается до TTL (`WithSchedulerLockTTL`, по умолчанию
  10с), иначе опоздавший на миллисекунды экземпляр дублирует тик. Для `AddEvery`
  exclusion точен только при одинаковом интервале на всех экземплярах.
- Документ расписания (`ScheduleStore`) — единый источник правды для next-тика:
  сохраняется при регистрации и после каждого срабатывания. Повторная
  регистрация с другим определением (task/interval/expr/timezone) —
  `ErrScheduleConflict`; payload менять можно. Упущенный тик (next в прошлом при
  активации): `CatchUpSkip` — сдвиг без запуска, `CatchUpFireOnce` — один
  догонный запуск. Задержки в рамках работающего цикла (downtime таймера)
  политикой не управляются.
- `Run` возвращает `nil` при штатной остановке (Stop/Shutdown/отмена ctx);
  повторный `Run` — ошибка.
- Дубликаты имён задач в планировщике отклоняются; `Remove(name)` возвращает
  ошибку для неизвестного имени.
